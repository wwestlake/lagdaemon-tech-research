## Context

The user asked for a full procedural imperative language — genuinely LALR(1)-parsed, compiling to an AST, optimized, and JIT-compiled to native machine code via LLVM — used to script game rules/logic/state, plus a node-based visual editor that produces/targets the same language rather than a separate parallel system. This is explicitly acknowledged as an enormous undertaking (half-joking: "would cause a human dev team to burst into flames"), so this plan is a multi-milestone roadmap, not a single implementation pass — matching the M/VFS/SC/AI milestone convention already used throughout this project (each milestone built, verified with real data, committed, and pushed before the next starts).

Two tooling forks were resolved by the user directly:
- **LALR(1) parser:** vendor **Bison + Flex** (e.g. WinFlexBison on Windows) as build-time code generators over `.y`/`.l` grammar files — same vendoring spirit as `third_party/cgltf.h`. Chosen over hand-rolling LALR table construction (first/follow sets, item sets, ACTION/GOTO tables) from scratch, which would be a huge, error-prone undertaking that isn't the interesting part of this project.
- **LLVM:** **vcpkg-managed LLVM**, `find_package(LLVM)`, using ORC JIT v2. Chosen over vendoring prebuilt binaries or building LLVM from source.

A codebase survey confirmed this isn't starting from zero: `NodeSystem/` (top-level module, sibling of `EngineCore`) already has `Graph`/`Node`/`Pin` classes with a `Domain` enum whose comment literally says *"one editor, one language, every domain"* — clearly seeded for exactly this, but it's pure data-model scaffolding today (no type registry, no serialization, no execution/codegen, no editor UI). `MainComponent.h`'s `exampleGraph_` member is dead code, never read anywhere. `EngineCore/` is otherwise just `World` (entt registry + tick clock, zero JUCE/GL deps) — the natural home for the language's framework-agnostic core. `docs/CAPABILITIES.md` §9 already states the design position *"No general-purpose visual scripting VM with its own bytecode interpreter and garbage collector"* — JIT-to-native is the spec's stated direction, not a new idea. §2's server requirements explicitly call for running "the same node graphs built in the authoring tool... inside this authoritative loop... just a new compiled rule module," which is exactly what this plan delivers.

**Milestone prefix: `GS`. Language name: CEL** (`.cel` source files, `.celg` node graphs, `celc` compiler/test-driver binary).

## Architecture decisions

**Module layout — new top-level `Language/` module**, not nested in `EngineCore`, matching `NodeSystem/`'s existing `include/<ns>/` + `src/` pattern:

```
Language/
  CMakeLists.txt
  grammar/cel.l  cel.y                     # Flex scanner, Bison C++ variant parser
  include/lang/
    ast.h  diagnostics.h  type.h  sema.h  compiler.h   # zero llvm/*.h, zero JuceHeader
    intrinsics.def                          # X-macro, single source of truth
    jit/runtime.h                           # opaque pimpl over LLJIT
    nodegen/node_catalog.h  graph_to_source.h
  src/  ...  src/jit/*.cpp                  # LLVM headers ONLY appear here
  tools/celc/main.cpp
  tests/{parse,sema,exec,host,nodegen}/
cmake/CelGrammar.cmake                       # bison/flex CMake wrapper (fills the currently-empty cmake/ dir)
```

Targets: `ce_lang_frontend` (no LLVM/JUCE/entt) → `ce_lang_jit` (+ LLVM, + `engine_core`) → `ce_lang_nodegen` (+ `node_system`, no LLVM) → `celc` (plain `add_executable`, deliberately **not** `juce_add_console_app`, so at least one build path never lets LLVM and JUCE headers meet). `engine_core` stays LLVM-free: it declares an abstract `IScriptRuntime`; `ce_lang_jit` implements it; both host executables link both and inject the concrete runtime at startup. Every `llvm/*.h` include is physically confined to `Language/src/jit/*.cpp` — a header firewall, not just a convention, so LLVM/JUCE/windows.h collisions become structurally impossible rather than something to remember.

**Language spec v1 — deliberately closed type system:** `int` (i64), `float` (f32, matches engine data exactly), `bool` (i1 SSA / i32 ABI), `vec3` (`{float,float,float}`, first-class with `.x/.y/.z` and arithmetic), `entity` (opaque i64 handle, no arithmetic, only `==`/`!=`/`is_valid()`), `void`. **No string type** — literals only, usable solely as intrinsic arguments (avoids needing heap ownership/refcounting/GC, consistent with CAPABILITIES §9). Deferred to v2: user `struct`s, arrays, `double`, string values, closures, generics, multi-file imports.

Declarations use leading keywords — `var x: float = 1.5;`, `func Name(p: type) -> type { }` — **not** C-style `type x = ...;`. This is a deliberate, permanent grammar-safety choice: C-style declarations create the classic "typedef problem" (`A * b;` is ambiguous between a declaration and an expression) the moment v2 adds user types, which requires lexer feedback and breaks LALR(1)-cleanliness. `var`/`func` keeps the grammar conflict-free regardless of future type growth. Assignment is a statement (`x = e;`, `x.y = e;`, compound `+= -= *= /=`), not an expression — removes the `if (x = 1)` bug class and a shift/reduce ambiguity. Control flow: `if/else if/else`, `while`, `for(init;cond;step)`, `break`, `continue`, `return`. Standard precedence via Bison `%left`/`%right`. `//` and `/* */` comments (non-nesting).

**Program shape** — explicit `self: entity` parameter (no implicit magic), lifecycle hooks `on_start`/`on_tick(self, dt)`/`on_stop`, file-scope `var` is **module-global, not per-entity** (documented loudly — the single most likely designer mistake).

**Host ABI — `extern "C"` trampolines, explicitly registered via ORC's `absoluteSymbols`, not `DynamicLibrarySearchGenerator::GetForCurrentProcess()`** (Windows `.exe` symbols aren't in the export table without `dllexport`, so process-scraping silently fails to find them). Six hard rules (written to `docs/SCRIPTING_ABI.md`): (1) aggregates never pass/return by value — `vec3` uses explicit pointer out-params, sidestepping MSVC x64's hidden-sret-pointer struct-return convention entirely; (2) only `int64_t/float/int32_t(bool)/uint64_t(entity)/const char*+len/float*/ScriptContext*` cross the boundary; (3) every trampoline is `noexcept`, reporting failure via a `ScriptContext` error flag — C++ exceptions unwinding through JIT'd Win64 frames need SEH/unwind-info registration the JIT doesn't provide; (4) generated IR has no `invoke`, every function is `nounwind`; (5) an opaque `ScriptContext*` is an implicit first parameter of every CEL function/intrinsic call (not thread-local — keeps multiple `World`s and compilation reentrant); (6) intrinsics are called with `World::RegistryMutex()` already held by the script phase caller and must not lock/block themselves.

A single `intrinsics.def` X-macro table (`CEL_INTRINSIC(name, c_symbol, ret, purity, params...)`) is the one source of truth consumed by sema, IR-gen, JIT registration, nodegen's auto-derived palette, and `docs/SCRIPTING_ABI.md` generation — mirrors how `ShaderComposer`'s GLSL chunk library keeps one authority per concept. The `purity` column (`Pure`/`ReadsWorld`/`Mutates`) drives LLVM function attributes correctly — critical because marking `get_position` as `readnone` would let the optimizer hoist it above a `set_position` and silently produce wrong game behavior; only true math intrinsics get `readnone`.

**How scripts run:** `ScriptComponent` (module + entry points + fault state) lives in `EngineCore/include/engine/script_component.h` — **not** `Source/Scene/Components.h`, because that layer is JUCE-facing (`juce::String`/`juce::Vector3D`) and `CreationEngineServer` can't see `Source/`, but the server must run identical designer-authored logic per CAPABILITIES §2. A new `Simulation::Step(World&, float dt)` in `EngineCore` becomes the one tick body both `MainComponent::timerCallback()` and the server's loop call: lock `RegistryMutex` → snapshot the `ScriptComponent` view (running scripts mutate the registry; iterating a live view during mutation is UB) → call `on_start` once then `on_tick` per entity → drain a deferred command buffer (destroy/component-add queued; spawn is immediate) → `AdvanceTick()` last. `dt` is a fixed timestep, never wall-clock, for reproducibility. A per-loop-back-edge budget-check call (inserted by IR-gen) stops runaway scripts from hanging the editor — explicitly documented as a robustness measure, not a sandbox (CAPABILITIES §5.2's modding/layered-content requirement means untrusted `.cel`/`.celg` content is a real future RCE concern once modding ships; v1 is trusted-author-only content, same trust level as this editor already assumes for arbitrary glTF/zip assets).

**Node graph → CEL: the graph emits textual CEL source**, which runs through the *identical* Flex/Bison/sema/IR-gen/JIT pipeline — not a separate direct-AST builder. Chosen because: it makes "one editor, one language" literal (a readable "View Generated Code" pane, hand-editable and paste-back-able); it's one code path instead of two parallel AST-construction APIs that will inevitably drift; diagnostics come free (sema errors are already keyed to source locations, and generated text reuses the same diagnostic engine via a source map + `// @node N` provenance comments back to node IDs); mixed visual/text authoring (a `Snippet` node splicing raw CEL) is trivial as text but requires invoking the parser on a fragment either way; and the performance cost of the extra parse (microseconds) is negligible next to LLVM's O2 pipeline (milliseconds).

**NodeSystem gets extended, not replaced** — add to `NodeSystem/`: a `NodeTypeRegistry` (fixes today's free-form, unvalidated `std::string` typeName), `Pin::defaultValue` (needed for unconnected-input codegen), `Node::editorX/editorY`, a hand-written line-oriented `.celg` serialization format (~150 lines, zero dependencies, git-diffable — deliberately not JSON, since NodeSystem currently links nothing), and structural analysis (exec-cycle detection, topological order, validation). **Codegen/execution stays in `Language/src/nodegen/`, not NodeSystem** — this is the one call that matters most: NodeSystem must stay backend-agnostic because the Material domain will eventually target GLSL via `ShaderComposer`, not CEL, and baking one backend into the shared substrate would break the "every domain" promise already written into `node.h`.

**Risks flagged explicitly (not silently absorbed):** (1) **C: has only 5.7GB free** — vcpkg root/buildtrees/binary-cache must all live on D:. (2) Build generator is **VS2019 (v142)**; recent LLVM/vcpkg increasingly assumes VS2022 — pin the vcpkg baseline to a commit with a known-good LLVM 17.x/18.x port, record the SHA, and treat "does it build on v142" as GS1's go/no-go signal before any further investment. (3) LLVM↔JUCE↔windows.h header collisions (`min`/`max` macros, `_ITERATOR_DEBUG_LEVEL` mismatch between Release LLVM and Debug engine builds) are real but reduced to a link-configuration problem by the header-firewall design — Debug builds will get noticeably heavier/slower to link, and that's named up front rather than discovered later. (4) Repo path `D:\000 Creation Engine` has spaces *and* starts with a digit — every Bison/Flex custom-command argument must be quoted. (5) No sandboxing in v1 — named as a pre-modding decision that must be made before GS's out of this plan's scope.

## Milestones

Ordered so the two things that could invalidate the whole plan — does vcpkg LLVM actually link/JIT in this exact environment, and is the grammar genuinely conflict-free LALR(1) — get proven first, before any large mechanical investment (full codegen, the node editor UI).

**GS1 — LLVM spike.** ✅ Complete. Prove vcpkg LLVM links and JITs here at all. No grammar, no engine integration — just `vcpkg.json` with a pinned baseline, `Language/`'s skeleton (`ce_lang_jit` + `celc` only), and a hand-built LLVM IR module (int add function + a call to an `extern "C"` host trampoline registered via `absoluteSymbols`) run through `PassBuilder` O2 + `verifyModule` + `LLJIT`. Also settles: exact LLVM version/vcpkg baseline SHA, VS2019-vs-VS2022, RTDyld-vs-JITLink (default RTDyld). **Verify:** `celc --selftest-jit` prints correct results and exits 0, registered as a CTest; `CreationEngineEditor`/`CreationEngineServer` still build and run in **both** Debug and Release after the LLVM link path is added (the concrete ABI-mismatch check).

**GS2 — Grammar, Flex/Bison integration, AST.** ✅ Complete. `cmake/CelGrammar.cmake`, `grammar/cel.l`+`cel.y` (Bison C++ skeleton, reentrant scanner, `%locations`), `lang/ast.h`, numbered diagnostics (`CEL1001`…), `celc --dump-ast`. **Grammar policy enforced at build time:** `%expect 0` plus `-Werror=conflicts-sr -Werror=conflicts-rr` — any shift/reduce or reduce/reduce conflict fails the build, which is the concrete mechanical proof of genuine LALR(1); dangling-else resolved via explicit `%precedence`, not Bison's default; `%glr-parser` banned by policy (a GLR escape hatch would silently void the LALR(1) requirement). **Verify:** the build itself failing on any conflict is the primary signal; `Language/tests/parse/*.cel` (~25 positive, ~15 deliberate syntax errors) round-tripped through `--dump-ast` and compared to committed `.expected` files via CTest, negative cases asserting diagnostic code + location (not prose).

**GS3 — Semantic analysis.** ✅ Complete. Scoped symbol table, type inference for `var x = e`, full type rules, control-flow checks (return-on-all-paths, break/continue-in-loop-only), intrinsics seeded from `intrinsics.def`, a minimal const-fold pass (only what's needed for diagnostics — LLVM does the real optimization later). **Verify:** `Language/tests/sema/` — positive programs must type-check clean, ~30 negative programs each asserting one specific diagnostic code/location, via CTest.

**GS4 — IR generation, optimization, execution (pure computation only, no engine intrinsics yet).** ✅ Complete. AST → LLVM IR (entry-block allocas so mem2reg/SROA promote to SSA), `PassBuilder` O0-O3, mandatory `verifyModule` before JIT, `celc --run`/`--emit-llvm`. **Verify:** `Language/tests/exec/*.cel` with `// expect:` headers (fibonacci iterative+recursive, loops, nested branches, vec3 math against hand-computed values, division/modulo edge cases) — each run at **both -O0 and -O2, asserting identical results** (the optimizer-correctness check).

**GS5 — Host ABI, intrinsics, ScriptContext, watchdog.** ✅ Complete. `EngineCore/include/engine/math.h` (POD Vec3), `engine/core_components.h`, `intrinsics.def` + its consumers, the implicit `ScriptContext*` threading, pointer-out-param vec3 convention, `absoluteSymbols` registration, purity-driven attributes, the budget-check watchdog, `docs/SCRIPTING_ABI.md`. (The `IScriptRuntime` abstraction itself was deliberately descoped one milestone later, to GS6, since `celc`'s own GS5 verification didn't need it — only the editor/server integration did.) **Verify — real data, not fabricated:** since `engine_core` has no JUCE dependency, `celc` links it directly and runs scripts against a **real `World`/`entt::registry`, headlessly** (`spawn_grid.cel`, `orbit_steps.cel` running 300 fixed-dt ticks) via `celc --run-world --ticks N`, comparing printed positions/checksums to `.expected` through CTest; an infinite-loop script must terminate via the watchdog with `CEL9001`.

**GS6 — Engine integration.** ✅ Complete. `ScriptComponent`, `IScriptRuntime`/`ICompiledScript`, `Simulation::Step` (the 5-step tick phase above) in `EngineCore`, `ce_lang_jit` implementing `IScriptRuntime` via `CelScriptRuntime`, both `MainComponent::timerCallback()` and the server's loop switched to call `Simulation::Step`. Also migrated `ce::scene::Transform` → a framework-agnostic `ce::engine::Transform` (mechanical but broad: `Components.h`, `ViewportComponent.cpp`, `TransformPanel.cpp`, `HierarchyPanel.cpp`), since scripts need to read/write positions and the server can't see `Source/Scene/Components.h`. **Verify, two signals:** (primary, deterministic) `CreationEngineServer --script orbit.cel --ticks 300 --dt D` produces **bit-identical** output to `celc --run-simulation` on the same script — direct proof of "runs identically client-side or server-side," as a CTest (`gs6_simulation_server_parity`), not UI automation; (confirmatory, visual) attached a hardcoded demo orbit script to a placed cube in the editor via computer-use — Play showed it genuinely orbiting (position matched the x²+z²=16 invariant read live from the Inspector), Pause froze it exactly in place, Stop fully reset it, and Play again ran a clean second cycle.

**GS7 — Script assets, in-editor code editor, hot reload.** 🚧 In progress. `.cel` as an Import-Hub-ingestible asset (`ScriptAssetImporter` + `ScriptCatalog`, mirroring the existing `AssetImporter`/`AudioCatalog` patterns), `Source/Views/ScriptPanel` (`juce::CodeEditorComponent` + `CelCodeTokeniser`), background-thread compilation via a `juce::Thread` (safe because GS2's parser is reentrant), atomic `ScriptComponent::compiled` swap under `RegistryMutex` picked up at the next `Simulation::Step`/`Refresh()` tick (old compiled program kept alive via `shared_ptr` until unreferenced — ordinary shared_ptr lifetime, no extra bookkeeping). **Verify:** edit a script's `speed`/`radius` value while playing, Compile, the entity's behavior changes within one tick with no restart (no `on_start` re-fire); measure and assert compile time **< 1s** (`celc --measure-compile`, a hard CAPABILITIES §3.5 requirement — measured, not assumed).

**GS8 — NodeSystem foundations (headless).** ⬜ Not started. `NodeTypeRegistry`, `Pin::defaultValue`, `Node::editorX/Y`, `.celg` serialization, structural analysis (cycle detection, topological order, validation). **Verify:** new `celc --selftest-graph` subcommand — build a graph programmatically, serialize/reload, assert structural equality; assert cycle detection and incompatible-pin-type rejection fire correctly; a committed `.celg` fixture must load unchanged (format-stability regression).

**GS9 — Graph → CEL source generation (headless).** ⬜ Not started. `ce_lang_nodegen`, a v1 Core/Event node catalog (OnStart/OnTick/Sequence/Branch/While/Compare/arithmetic/MakeVec3/Get-SetPosition/Spawn/Destroy/Log/variable get-set/CallFunction), topological exec-chain walk emitting statements, the source map, `celc --graph-to-source`/`--run-graph`. **Verify — the strongest test in the plan:** `Language/tests/nodegen/` holds paired `.celg` graphs and hand-written `.cel` references that should be semantically identical; both run through `celc --run-world` against a real `World` for a fixed tick count and must produce **identical final world state** — this single test validates the graph, generator, parser, sema, IR-gen, optimizer, and ABI together, proving the graph and text really are one language.

**GS10 — Node editor UI.** ⬜ Not started. New `WorkspaceMode::Logic` tab, `Source/Views/NodeEditor/{NodeGraphComponent,NodePalette,NodeInspector,GeneratedCodeView}` (canvas pan/zoom, drag-to-position persisted to `Node::editorX/Y`, wire dragging with live `IsConnectionCompatible` feedback per CAPABILITIES §4.1's "flagged at author time," palette from `NodeTypeRegistry`, read-only generated-code view, Save/Load `.celg`, Compile & Attach to selected entity) — finally makes `exampleGraph_` real or removes it. **Verify:** hand-build a small graph (OnTick→Branch→SetPosition) in the UI, screenshot, Compile & Attach, confirm the entity's behavior changes in the viewport (screenshot); then verify the UI-saved graph headlessly via `celc --run-graph` against expected world state, so the UI is checked through the already-trusted headless path.

**GS11 — Sub-graphs, error surfacing, trace hooks.** ⬜ Not started. Reusable sub-graphs compiling to generated `func`s + a `CallSubgraph` node, diagnostics mapped back through the source map to highlight the offending node, optional `--trace` compile mode for CAPABILITIES §8's traceable rule/event execution logging. **Verify:** a subgraph called twice emits one `func` + two call sites (diffed generated source); a broken node input highlights that specific node, not an opaque error; trace output matches a committed expected trace.

## Explicitly out of scope (write down now so it doesn't silently creep in later)

User `struct`s/arrays, a real `string` type, per-entity script fields, the Animation/Material/Audio node domains (Material targets GLSL via `ShaderComposer`, which is exactly why codegen stays out of NodeSystem itself), network replication of script state, cross-machine float determinism, an untrusted-content sandbox, node-editor undo/redo (belongs to a future editor-wide undo effort, not scripting specifically).

## Critical files

- `CMakeLists.txt` — vcpkg toolchain wiring, `CE_ENABLE_SCRIPTING` option, `add_subdirectory(Language)`, `enable_testing()`
- `EngineCore/include/engine/world.h` — the `RegistryMutex`/`AdvanceTick` contract every intrinsic and `Simulation::Step` must honor; sibling home for `script_component.h`/`script_runtime.h`/`simulation.h`/`core_components.h`
- `NodeSystem/include/node_system/{node.h,pin.h}` — where the type registry, pin defaults, and editor positions get added; `DataType` is nodegen's mapping table
- `Source/Scene/Components.h` — `Transform` migration (GS6) started here, rippled to `ViewportComponent.cpp`/`TransformPanel.cpp`/`HierarchyPanel.cpp`
- `Source/MainComponent.cpp` (`timerCallback`) and `Server/Source/Main.cpp` (its main loop) — both now call the same `Simulation::Step`, which is what makes "client and server run identical logic" actually true instead of aspirational

## Sizing/risk at a glance

GS1 and GS2 were the highest-risk, smallest-scope milestones (each could have invalidated a tooling choice) and came first deliberately — both came back clean. GS6 and GS9 are the largest/most mechanical (GS6 is done; GS9 is still ahead). GS10 (the visual editor) is the biggest single UI effort but lowest technical risk, since by then the entire pipeline underneath it will already be proven headlessly.
